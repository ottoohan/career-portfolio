# 메모리 파일 예시 4종

파일 하나 = 사실 하나. `MEMORY.md`에는 한 줄 포인터만 둔다.

---

## feedback — 일하는 방식 지시 (왜 + 어떻게)

```markdown
---
name: feedback_ticket_problem_expected_split
description: 결함 티켓은 맨 위에 '문제'와 '기대 결과'를 분리해 쓴다 — 추정은 아래 별도 섹션
metadata:
  type: feedback
---

티켓 본문은 `## 문제` → `## 기대 결과` 순서로 시작하고, 원인 추정·확인 요청은 그 아래에 둔다.

**Why:** 담당 개발자 피드백 — 현상·실측·추정·제안을 한 덩어리로 써서 무엇을 바라는지 알기 어렵다.
같은 날 추정을 사실처럼 쓴 티켓 하나는 개발자 조사 후 철회됐다.
**How to apply:** 티켓 생성·재확인 코멘트 모두. 추정은 "추정·미확인" 표기.
```

## project — 진행 중인 일 (현재 상태가 핵심)

```markdown
---
name: project_<티켓>_<요지>
description: <무엇이 왜 문제인지 한 줄>
metadata:
  type: project
---

<사실 3~5줄: 원인, 영향 범위(실측 시각 포함), 결정 필요 A/B>

**Why:** <이 기록이 왜 필요한가 — 예: 지난번 기록만 하고 티켓을 안 만들어 재발>
**How to apply:** 대기: <다음 관문> → <그다음>
```

## reference — 환경 함정 (증상 → 원인 → 대처)

```markdown
---
name: reference_db_staleness_check
description: "실시간" 조회 DB도 갱신이 멈출 수 있음 — "없음" 판정 전에 최신성부터 확인
metadata:
  type: reference
---

<날짜>에 최신 행이 40분 전에 멈춰 있었고, 이를 모르고 "0행"으로 판정했다가 철회했다.

**How to apply:** "0건" 판정 쿼리에는 현재 시각과 활성 테이블 MAX(created_at)을 같이 본다.
차이가 몇 분 이상이면 "미확인"으로 둔다.
```

## user — 나는 누구인가

```markdown
---
name: user_role
description: <직무>, <담당 범위>
metadata:
  type: user
---

<직무>로 <팀 A>와 <팀 B>를 동시에 맡는다. 최종 판단 기준은 "검증 가능한가".
코드도 직접 고치지만, 기초 설명은 필요 없다.
```

## 버그 패턴 DB (교차 패턴)

사례가 2건 이상 모이면 패턴으로 묶는다. TC 설계와 원인 분석의 체크리스트가 된다.

| 패턴 | 정의 | 사례 수 |
|---|---|---|
| PT-01 조용한 실패 | 에러 없이 결과만 틀림(null 반환, 이벤트 유실, 상한 잘림) | |
| PT-02 FE 미소비 | 백엔드는 필드를 내려주는데 프론트가 안 씀 | |
| PT-03 목록/건수/엑셀 불일치 | 같은 조건이 세 곳에 따로 복사됨 | |
| PT-05 캐시 | 바꿨는데 안 보임 — 캐시 키·무효화 경로 | |
| PT-07 시각 경계 | 시간대·자정·기간 포함 여부 | |
| PT-08 0건 오판 | 데이터 최신성·권한·필터 때문에 0으로 보임 | |
| PT-10 폴백 은폐 | 대체 경로가 '성공'으로 집계됨 | |
