## 한 줄 소개

**지원 직무: QA + 운영지원(Product Operations).** 결함을 막는 QA에, 운영자가 쓰는 도구를 고치고 운영 문의를 판정해 닫는 운영지원을 더했습니다. 원인은 코드에서 찾고, 고칠 수 있는 건 직접 고치고, 결과는 다시 잽니다.

QA 엔지니어로 입사해 릴리스 관리 → 팀 리드·채용 → 요구사항 기획 → 백오피스 KR 오너 순으로 역할을 넓혔습니다. 공식 직무는 끝까지 QA였습니다.

# 주요 업무

## 0. 운영지원 — 운영 문의를 판정하고 닫기

**상황** — 운영 부서(강의 운영·CS·마케팅)의 문의가 개발본부 지원 채널로 한 달 약 60~150건 들어왔다. 같은 실수와 같은 질문이 반복됐는데, 무엇이 결함이고 무엇이 사용법 문제인지 가르는 공통 기준이 없었다.

**행동**
- **판정 틀** — 문의마다 "시스템 결함 / 운영 실수·동작 오해 / 정책 문의"를 먼저 가르고, 운영 조치로 오늘 끝낼 수 있는지, 개발이 필요한지까지 한 답글로 정리한다. 결함이어도 우회를 먼저 주고 근본 수정은 티켓으로 넘긴다. 형식을 AI 스킬로 고정해 누가 받아도 같은 틀로 답하게 했다 → [사례 12](cases/12-ops-inquiry-triage.md) · [플레이북 09](../4-qa-playbook/09-ops-inquiry-triage.md)
- **알리는 일** — 운영 부서 채널에 직접 올린 운영지원 메시지 345건 이상(2025.01~2026.11, 키워드 검색 기준 최소치). 공지는 "배경 → 바뀐 점 → 사용 방법 → 유의사항" 순서로 고정했다 → [플레이북 10](../4-qa-playbook/10-ops-notice.md)

  | 유형 | 건수 | 예 |
  |---|---|---|
  | 정책·사용법 안내 | 66 | 문자 발송이 자동으로 걸러지는 조건, 수강후기가 언제·어떤 설정에서 노출되는지, 이미 있는 기능의 사용법 |
  | 새 기능 배포 안내·시연 | 95 | 잔여수량 표시 설정 어드민화(시범 운영 + Q&A 세션), 동영상 일괄 등록(대면 가이드), 조편성 엑셀 업로드 |
  | 운영 문제 대응 | 184 | 외부 영상 서버 장애 시 고객 응대 가이드, 탈퇴가 막히는 문제의 원인과 우회 방법 |

  2025년에는 문제 대응이 대부분이었고, 2026 상반기부터 배포 안내가 문제 대응을 앞섰다.
- **가드** — 운영 실수가 반복되던 자리에 저장 전 차단·안내를 넣었다(프론트 단독은 직접 구현, 서버 변경은 개발자와 함께).
- **측정** — 챕터 주간 미팅에서 손으로 하던 유형 분류를 같은 정의로 월 비율로 다시 쟀다. 분류 틀은 하나다: 답글에서 쓰는 판정 3분류(시스템 결함 / 운영 실수·동작 오해 / 정책 문의)에, 집계할 때만 권한·데이터 작업 요청을 "협업 요청"으로 따로 센다.

**결과 — 내 몫 ①: 내가 판정한 문의가 어떻게 닫혔나**

지원 채널에서 내가 답한 스레드를 전수로 다시 읽어, 종결 시각과 14일 안에 같은 요청자가 같은 주제로 다시 물었는지를 셌다. 비교군은 같은 기간 내가 답하지 않은 스레드다.

| 지표 | 2025.12 (내가 답한 84건) | 2026.10.01~11.14 (내가 답한 55건) | 같은 기간 내가 답하지 않은 건 |
|---|---|---|---|
| 당일 종결 | 51% (43/84) | **73% (40/55)** | 59% (22/37) |
| 개발이 필요 없는 문의의 당일 종결 | 69% (34/49) | **76% (22/29)** | 68% (19/28) |
| 개발 필요 건: 티켓·담당을 당일 안내 | 74% (26/35) | **92% (24/26)** | 9건뿐이라 비율 생략 |
| 14일 내 같은 주제 재문의 | 1/66 | **0/37** (14일을 다 본 건) | 0/21 |
| 끝까지 결론이 안 난 스레드 | 18 | 2 | 5 |

- 정의: 종결 = 요청자 확인, "조치·배포 완료", 스레드 안 메시지의 완료 표시, 또는 운영 안내 뒤 이견 없이 끝난 경우의 그 안내 시각. 개발 필요 건은 수정 배포가 아니라 "티켓 번호·담당 배정을 안내한 시각"을 운영 단계 종결로 따로 셌다(실제 수정이 당일 끝난 건은 26건 중 18건).
- 한계: 종결 판정과 "같은 주제" 판정은 AI가 스레드를 읽고 했다(200건 중 59건은 확신도 낮음). 스레드 안에서 다시 열린 경우는 재문의로 세지 않아 재문의율이 낮게 잡혔을 수 있다. 2025.12와 2026.10~11은 개발 필요 건 비중이 달라(42% vs 47%) 전체 당일 종결률보다 "개발이 필요 없는 문의"끼리 비교하는 편이 공정하다.

지원 채널 인입 868건(2025.12~2026.10)을 같은 정의로 분류하고, 내가 넣은 가드가 겨냥한 실수 유형만 골라 배포 전후 건수를 셌다. "기대"는 배포 전 월평균대로라면 배포 후에 나왔어야 할 건수다.

운영 실수가 원인인 요청은 11개월 합계 94/868 = 10.8%이고, 월별로 2.6~15.5%를 오르내릴 뿐 **뚜렷하게 줄지 않았다.** 가드로 막은 유형은 사라졌지만 그 자리에 다른 유형(노출 설정, 판매 기간, 기능을 몰라 수기 처리한 건 등)이 새로 생겼다. 처음에는 2025.12(13.9%)과 2026.05~10 합산(9.7%)만 비교해 줄었다고 적었는데, 빈 달을 채워 보니 그 비교는 구간 선택에 기댄 값이라 철회했다.

**읽을 때 주의**
- 분류는 AI가 스레드 결론을 읽고 했다. 2025.12·2026.05~10은 같은 정의로 일괄 재판정했고 무작위 20건을 내가 검수해 20/20 일치했지만(AI 판정을 함께 본 검수라 독립 검증은 아님), 2026.01~04·08은 재판정을 거치지 않았다.
- 가드 다수가 사고 직후 며칠 안에 배포된 반응형이라, 배포 전 건수에 계기가 된 사고가 들어 있다. 사고가 몰린 시기 직후를 재는 셈이라 평균으로 돌아가는 효과가 섞여 있을 수 있다.
- 분류 모수 868건은 2025.12~2026.10.30 최상위 인입이고, 요청 건수 774건은 채널 전체 기록의 1~10월 집계라 집계 시점·기준이 달라 합이 맞지 않는다.
- 응답 시간·종결 유형은 2025.12과 2026.10~11.14, 요청 건수는 채널 전체 기록이 있는 1~10월로 지표마다 비교 구간이 다르다.

## 1. 운영자 백오피스를 프로덕트로 만들기

**상황** — 사내 운영 도구는 요청이 들어오면 그때그때 고치는 구조였고, 개선 효과를 확인할 지표가 없었습니다.

**판단** — 내부 도구에도 사용자가 있습니다. 사용자·지표·개선 사이클을 붙이면 프로덕트로 다룰 수 있다고 봤습니다.

**행동**
- **핵심 목표(KR) 오너십**: 백오피스 관련 문의 인입 절감을 목표로 잡고, 선행지표(개선 작업량)와 후행지표(문의 인입·운영 실수 비율·만족도)를 양쪽으로 설계
- **월간 의견 조사**: 고정 문항 3개로 매달 조사(2026.04~10, 5월 미실시)하고, 의견마다 코드에서 원인을 확인해 범위(프론트 단독 / 서버 변경 / 스키마 변경)로 나눔. 모든 응답에 처리 현황을 회신 → [플레이북 11](../4-qa-playbook/11-ops-feedback-loop.md)
- **월간 조치 리포트**: 배포 PR·조치 영역·참여 개발자를 월 단위로 집계해 공유
- **반기 회고**: 6개월간 팀 전체 백오피스 변경 169건(프론트 102 + 백엔드 67, 작은 수정 포함 — KR 집계와 기준이 다름)을 영역별로 정리해 다음 반기 우선순위 도출

**결과**
- 개선 PR 머지 25 → 49건 (보조 지표 — KR 집계, 팀 합계, 작업량이라 효과를 뜻하지 않음)
- 9월 회차 의견 20건 중 **완료 12 · 백로그 8**, 백로그도 사유를 적어 회신
- 장기 과제로 잡았던 예약·일괄 업로드 기능 배포 후, 해당 항목이 다음 조사에서 불만이 아닌 칭찬 코멘트로 회귀
- 만족도 8.23 → 9.33(보조 지표). 6월·9월에 한 번씩 내려갔다 → [사례 01](cases/01-backoffice-as-product.md)

## 2. 요구사항과 정책을 정의하기

**상황** — 검증 단계에서 발견되는 문제 중 상당수는 버그가 아니라 **정책이 정해지지 않은 것**이었습니다. 코드를 고쳐도 다음 달에 같은 문제가 돌아왔습니다.

**행동**
- **요구사항 정의서(PRD) 12건 이상** — 기획 담당자로 이름을 올리고 프론트·백엔드 개발자와 협업
  - 고객 알림 발송 시스템 외부 벤더 → 자체 백오피스 내재화(1·2차), 개인정보 이용내역 통지·마케팅 수신동의 재확인(법정 의무 대응), 결제 페이지 쿠폰 자동 적용, 수강률·과제 완수율 지표 개편, 강의 이어보기, 콘텐츠 공개 예약 등
- **정책서 6건 이상** — 환불, 수강률 산정 기준(v2.0), 첫구매 쿠폰, 홈 콘텐츠 편성, 상품 복제 대상 필드, 구매 긴급성 노출 가이드
- **설계 문서** — 결제 옵션·수단 변경(원주문 유지 + 차액 정산, 6개월간 실제 옵션 변경 이력을 실측해 근거로), 조 편성 노출 예약, 조 채팅방 링크 자동 안내. 기획 검토용 와이어프레임은 인터랙티브 HTML로 만들어 링크로 공유
- **정책 결함 제기** — 앱/웹 가격 역전(특정 전환 시점에 앱보다 웹이 비싸지는 구조), 판매 기수 공백기마다 대표 강의가 필터에서 사라지는 구조, 알림 금액 스냅샷 재발 → [사례 06](cases/06-price-snapshot-recurrence.md)

**결과** — 회사 표준 PRD 규격(도메인 용어 사전 / 요구사항 번호 / 상태·행동·결과 표 / 확인 필요 마커)으로 12건 이상을 작성했습니다.

## 3. 데이터로 의사결정하기

**상황** — 기능을 내보낸 뒤 효과를 확인하는 절차가 정해져 있지 않아, 다음 결정의 근거가 약했습니다.

| 질문 | 분석 | 바뀐 결정 |
|---|---|---|
| 시즌 프로모션의 결제를 누가 이끌었나 | 결제 기여 비중: 홈 배너 14.7% vs 실시간 방송 플로팅 창 2.16% (제품 분석 도구 기준) | 다음 시즌 배치 우선순위 변경(가설 반증) |
| 오픈 알림 신청자가 왜 결제까지 안 오나 | 퍼널 이탈의 병목은 발송 부족이 아니라 알림 클릭률 | 발송 증량안이 효과 없음을 보여 줌 |
| QA 지원 요청이 왜 밀리나 | 4주 인입 분류: 요청이 특정 인원에 집중, 즉시 대응이 필요한 건은 약 3분의 1 | 나머지는 배치 처리로 전환 |
| 검색 유입이 왜 크게 줄었나 | 유입 경로별 분해(유료는 증가, 검색만 급감) → 색인·노출·크롤 지표 → 봇 크롤 표본 30건 → 검색엔진 업데이트 일정 대조 | 색인은 정상이고 절벽 날짜가 코어 업데이트와 일치 → 기술 원인을 닫고 콘텐츠 품질 대응으로 범위 한정 |

- **개발 공수 산정**: 외부 AI 상담 API 연동 건에 대해 코드베이스 3개 레포를 직접 확인해 팀별 소요 리소스를 산정하고, 고객지원·개발·기획 3개 팀의 우선순위 논의 자료로 제공
- **우선순위 프레임**: 매출이 집중되는 핵심 사용자 경로를 식별해 테스트·개선 우선순위의 기준 문서로 정의(이후 크리티컬 유출률의 "크리티컬 영역" 기준이 됨)

## 4. 스쿼드 일정을 설계하고 팀을 조율하기

**상황** — 스쿼드의 한 달 일정이 한곳에 정리되어 있지 않아, 무엇을 언제 누가 하는지가 사람마다 다르게 이해되면서 일정 충돌과 대기가 반복됐습니다.

**행동**
- **스쿼드 월간 플래닝 오너** — 매월 진행할 항목을 티켓 단위로 분해하고, 각 직군(기획·디자인·프론트·백엔드·QA) 담당자와 예상 일정을 협의해 간트 차트로 편성. 목표·요구사항 문서·티켓·담당자·소요 일수를 한 시트에서 관리하며 매월 갱신
- **구성원별 목표 설계** — 구성원마다 다른 축의 목표를 두되, 모든 지표가 같은 데이터를 쓰도록 단일 측정 소스를 정의(지원 요청 인입을 4개 유형으로 태깅)
- **채용 과제 평가 4명** — 테스트 설계·협업 질문 능력 평가 배점 기준을 만들고 실제 평가 수행
- **온보딩 설계** — 온보딩 체크리스트·직무 롤 정의 문서, 신규 입사자 온보딩 평가서(역량 등급 + 보완 계획)
- **크로스 챕터 의사결정 퍼실리테이션** — 자동화 테스트 역할분담 확정 회의를 사전 의견 수집 → 역할 표 확정 순서로 설계
- **챕터 주간 미팅 2년 운영** — 인입 건을 4개 유형으로 사람이 분류·집계(이 데이터를 월 비율로 다시 잰 것은 0절)

## 5. 코드를 읽고, 직접 고치기

공수 산정도 정책 진단도 코드에서 나왔습니다. 고칠 수 있는 건 직접 고쳐 배포했고, 권한 밖의 것은 원인과 수정안을 담당자에게 인계했습니다. 코드 작성에는 AI 에이전트를 쓰고, 원인 진단·기대 결과 정의·검증·배포 확인은 직접 맡았습니다.

**프로덕션 레포 직접 커밋 328건** (2026.02~11, 기본 브랜치 반영 기준) — 백오피스 프론트 161 · 사용자 프론트 110 · 메인 백엔드 45 · 백오피스 API 10 · 기타 2개 레포 2. 커밋 메시지로 나누면 기능 약 40%, 결함 수정 약 36%, 되돌림 약 2%(8건, 그중 2건은 정책 보류로 되돌림).

**직접 고친 것(대표)**
- 백오피스: 세션 갱신 대기열이 폐기되며 요청이 사라지던 "무반응" 결함, 모달 드롭다운이 마스크 뒤에 깔리던 결함, 할인율 입력이 판매가를 바꾸던 결함, 오랫동안 빈 함수였던 팝업 복제, 날짜 포맷 분·월 뒤바뀜, 필수 강의 수강률 0% 저장 차단
- 사용자 웹: 예외 없이 null을 돌려주는 코드가 폴백을 끊어 안내 팝업이 안 뜨던 문제, 백엔드의 "공개 예약" 필드를 소비하지 않아 예약 교재가 노출되던 문제, 대기 신청 상태의 공유 버튼 누락, iOS 다운로드 파일명 핫픽스
- 백엔드: 고객 검색 결함(와일드카드 이스케이프 누락 + 건수 쿼리 조건 불일치) → [사례 04](cases/04-search-zero-results.md), 환불 관리 상품번호 검색, 상품별 통계 개선(알림 후 결제 인원·전환율, 운영 수치를 원천 DB와 대조해 통과), 선착순 마감 해제, 대기 취소 알림 선택 발송

**원인을 찾고 인계한 것** — 페이지 이동 직전 분석 이벤트 유실(SDK 직렬 전송 구조까지 재현) → [사례 03](cases/03-event-loss-before-navigation.md), 수강기간 일괄 변경의 2,000건 잘림 → [사례 05](cases/05-silent-2000-cap.md), 브랜치 머지 전략이 SQL 매퍼 정의를 유실시킨 런타임 500, 백오피스 변경이 사용자 화면에 반영되지 않던 영구 캐시

**품질 기반**
- 결제 도메인 전수 TC 290건 — 레거시 결제 흐름을 문서로 지도화하고, 과거 결함 101건을 TC와 하나씩 대응시켜 누락 경로를 점검. 동료가 도입한 E2E 기반 위에 결제 시나리오 36건을 자동화, 자동화 실패 2건이 모두 실결함
- 사고 뒤 TC 설계 기준 재수립 — 유형 매트릭스·미지원 가드·폴백 은폐·폴백 내용 4묶음, 2차 QA에서 배포된 범위 43건 중 35건 수행(통과 29 · 실패 6), 8건 미수행 → [사례 07](cases/07-fallback-masked-as-success.md)
- 부하 테스트(2025.03, 팀 공동 수행·결과 보고서 작성) — 목표 부하(5분 약 18만 요청)의 약 2.7배까지 지연 없음, 프론트 CPU 75%를 지연 경계로·DB CPU를 먼저 오는 병목으로 규명, 인스턴스당 처리량으로 증설 대수 산정(재측정에서 처리량 약 20% 감소를 찾아 재산정)
- 전사 웹 성능 진단 — 저하 원인 9종, 실사용자 성능 데이터가 수집되지 않는 관측 공백 지적

**AI 업무 환경과 AI 결과물 평가** (자세히 → [AI 활용 부록](../3-why-me/ai-appendix.md))
- 규칙서·메모리·독립 검증 에이전트·훅·조회 래퍼로 업무 환경을 구조화, 세션 로그로 재고 고침 → [사례 08](cases/08-ai-agent-qa-workflow.md). 점검 중 커밋 품질 훅이 6개월간 동작하지 않던 것을 발견해 push 훅을 다시 작성(38개 입력 테스트)
- 사내 AI 개발 프레임워크 QA 트랙 목표·측정 관리 — TC 생성 스킬 초기 버전 설계(이후 동료가 통합·확장해 챕터 공용 v3.3), 프레임워크 회귀 E2E spec 6개(결제 E2E 36건과 별개)
- RAG 평가 실험 — 질문 40개·3회 다수결·AI 채점자 보정으로 병목이 찾기임을 실측, 사내 RAG 스터디 4부 발표 → [사례 10](cases/10-rag-evaluation.md)
- 관심강의 온톨로지 QA 검토 — 시점 누수 판별·예측 구간화 → [사례 11](cases/11-ontology-review.md)

**장애 대응** — 고객 메시지 발송 장애 타임라인 정리와 원인 회고록(포스트모템) 작성

## 원인은 규명했으나 반영되지 않은 건

- **강의 필터의 판매 상태 의존** — 구조적 리스크 제기, 미착수
