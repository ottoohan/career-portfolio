# 주요 업무

## 1. 운영자 백오피스를 프로덕트로 만들기

**상황** — 사내 운영 도구는 주인이 없었습니다. 요청이 들어오면 그때그때 고치는 구조라, 무엇이 문제인지도 무엇이 나아졌는지도 아무도 몰랐습니다.

**판단** — 내부 도구에도 사용자가 있습니다. 사용자·지표·개선 사이클을 붙이면 프로덕트로 다룰 수 있다고 봤습니다.

**행동**
- **핵심 목표(KR) 오너십**: 백오피스 관련 문의 인입 절감을 목표로 잡고, 선행지표(개선 작업량)와 후행지표(문의 인입 수·만족도)를 양쪽으로 설계
- **정기 만족도 조사 운영**: 실사용 부서를 대상으로 분기 조사를 정착시키고, 응답을 유형별로 분류해 단기/장기 개선 백로그로 전환
- **월간 조치 리포트 체계**: 배포 PR·조치 영역·참여 개발자를 월 단위로 집계해 공유 (예: 한 달 배포 PR 45건·조치 영역 10개·참여 개발자 6명, 팀 합계)
- **반기 회고**: 6개월간 팀 전체 백오피스 개선 169건(프론트 102 + 백엔드 67)을 영역별로 정리해 다음 반기 우선순위 도출

**결과**
- 만족도 **7.29 → 8.82**로 역대 최고 갱신
- 개선 PR 머지 **+96%**, 월평균 운영개선 PR **+50%** (개발자들과 함께 낸 팀 합계)
- 장기 과제로 잡았던 예약·일괄 업로드 기능 배포 후, 해당 항목이 다음 조사에서 불만이 아닌 **칭찬 코멘트로 회귀**

> 개선했다는 주장이 아니라, **같은 사람들에게 같은 질문을 반복해서 수치 변화를 만든 것**이 이 일의 핵심입니다.

## 2. 요구사항과 정책을 정의하기

**상황** — 검증 단계에서 발견되는 문제 중 상당수는 버그가 아니라 **정책이 정해지지 않은 것**이었습니다. 코드를 고쳐도 다음 달에 같은 문제가 돌아왔습니다.

**판단** — 하류에서 막을 게 아니라 상류에서 정의해야 합니다.

**행동**
- **요구사항 정의서(PRD) 12건 이상 직접 작성** — 문서상 기획 담당자로 이름을 올리고 프론트·백엔드 개발자와 협업
  - 고객 알림 발송 시스템 외부 벤더 → 자체 백오피스 내재화 (1·2차)
  - 개인정보 이용내역 통지·마케팅 수신동의 재확인 (법정 의무 대응)
  - 결제 페이지 쿠폰 자동 적용
  - 수강률·과제 완수율 지표 개편, 강의 이어보기, 콘텐츠 공개 예약, 주문 관리 필터 개선 등
- **정책서 6건 이상** — 환불 정책, 수강률 산정 기준(v2.0), 첫구매 쿠폰, 홈 콘텐츠 편성, 상품 복제 대상 필드, 구매 긴급성 노출 가이드
- **의사결정 문서** — 독려 메시지 발송 운영 개선(배치 자동화 vs 통합 관리 페이지 비교), 지표 재계산 시점 정책
- **정책 결함 제기**
  - 앱/웹 가격 역전: 할인 정책 구조상 특정 전환 시점에 앱보다 웹이 비싸지는 문제를 발견해 정책 재정의 요청
  - 강의 필터가 "현재 판매 중인 기수 존재 여부"에 묶여 있어, 기수 공백기마다 대표 강의가 목록에서 사라지는 구조적 리스크 제기

**결과** — 회사 표준 PRD 규격(도메인 용어 사전 / 요구사항 번호 / 상태·행동·결과 표 / 확인 필요 마커)으로 12건 이상을 작성했습니다.

## 3. 데이터로 의사결정하기

**상황** — 기능을 내보내고 나면 잘 됐는지 아무도 확인하지 않았습니다. 다음 결정은 감으로 내려졌습니다.

**행동**
- **성과 계측을 처음부터 끝까지 설계** — 계측 키 정의 → 대시보드 구축 → 결과 해석까지 (제품 분석 도구·SQL 대시보드)
- **가설 반증**: 시즌 프로모션에서 실시간 방송 플로팅 창이 결제를 이끌 것이라 가정했으나, 실측 결과 **결제 기여는 홈 배너가 플로팅 창의 약 7배**. 다음 시즌 배치 우선순위를 바꾸는 근거가 됨
- **조직 리소스 정량 진단**: 사내 지원 요청 채널 4주 인입을 분류한 결과 요청이 특정 인원에 집중돼 있었고, 그중 **즉시 대응이 필요한 건은 약 3분의 1**뿐임을 보여 나머지는 배치 처리로 전환 가능하다는 결론 도출
- **우선순위 프레임**: 매출이 집중되는 핵심 사용자 경로를 식별해 테스트·개선 우선순위의 기준 문서로 정의
- **개발 공수 산정**: 외부 AI 상담 API 연동 건에 대해 **코드베이스 3개 레포를 직접 확인해** 팀별 소요 리소스를 산정하고, 고객지원·개발·기획 3개 팀의 우선순위 논의 자료로 제공
- **대형 프로모션 사전 검수**: 시즌 프로모션 판매 상품 29종의 4단계 가격 설계 정합성을 교차 검증해 **이상값 8건을 오픈 전 차단** (종료일 오타, 옵션명 오기 등)

## 4. 스쿼드 일정을 설계하고 팀을 조율하기

**상황** — 스쿼드의 한 달 일정이 어디에도 한눈에 정리되어 있지 않았습니다. 무엇을 언제 누가 하는지가 사람마다 다르게 이해되면서 일정 충돌과 대기가 반복됐습니다.

**행동**
- **스쿼드 월간 플래닝 수립·운영 (오너)** — 매월 스쿼드 전체가 진행할 항목을 **티켓 단위로 전부 분해**하고, 각 직군(기획·디자인·프론트·백엔드·QA) 담당자와 **예상 일정을 협의해 간트 차트로 편성**. 목표(KR)·요구사항 문서·티켓 링크·담당자·직군별 소요 일수를 한 시트에서 관리하며 매월 갱신. 이슈 트래커에도 일정 관리 전용 프로젝트를 두고 월별 일정 에픽을 운영
- **구성원별 목표 설계** — 구성원마다 다른 축의 목표를 두되, **모든 지표가 같은 데이터를 쓰도록 단일 측정 소스를 정의**(지원 요청 인입 건을 4개 유형으로 태깅)
- **채용 과제 평가 4명** — 테스트 설계·협업 질문 능력 평가 배점 기준을 만들고 실제 평가 수행
- **온보딩 설계** — 온보딩 체크리스트와 직무 롤 정의 문서 작성, 신규 입사자 온보딩 평가서 작성(역량 등급 + 보완 계획)
- **크로스 챕터 의사결정 퍼실리테이션** — 자동화 테스트 역할분담(RNR) 확정 회의를 "정답을 찾는 자리가 아니라 합의를 만드는 자리"로 설계, 사전 의견 수집 후 역할 표 확정
- **전환 로드맵** — 챕터의 AI 활용 전환 계획 수립 (현행 업무 분해 → 표준화 요건 → 마일스톤)
- **정기 운영 체계** — 챕터 주간 미팅을 2년간 운영하며 인입 건을 4개 유형(운영 실수/버그/협업 요청/정책 문의)으로 분류·집계하는 체계 정착
- **2개 스쿼드 동시 담당** — 인터럽트 발생 시 일정 재조율, 스쿼드 간 정책 충돌 사전 차단

## 5. 코드를 읽고, 직접 고치기

공수 산정도 정책 진단도 코드에서 나왔습니다. 그리고 상당수는 직접 고쳐서 배포했습니다. 코드 작성에는 AI 에이전트를 쓰고, 원인 진단·검증·배포 확인은 직접 맡았습니다.

**프로덕션 레포 직접 커밋 328건** (2026.02~11, 기본 브랜치 반영 기준 / 백오피스 프론트 161, 사용자 프론트 110, 메인 백엔드 45, 백오피스 API 10, 기타 2)

**근본 원인 진단 사례**
- **브랜치 머지 전략이 원인이던 런타임 500** — 특정 머지 방식이 SQL 매퍼 정의를 유실시켜, 증상은 화면 오류지만 원인은 배포 전략 자체였음을 규명
- **조용한 null 반환이 끊은 폴백 체인** — 예외 없이 null을 돌려주는 코드가 후속 분기를 통째로 건너뛰게 만들어 안내 팝업이 뜨지 않던 문제
- **영구 캐시 미무효화** — 백오피스에서 바꾼 내용이 사용자 화면에 **영영 반영되지 않는** 구조를 발견, 운영 오픈 전 수동 퍼지 절차 정립
- **게시판 연쇄 삭제 비대칭** — 강의 연결을 교체해도 기존 제출물이 따라오지 않아 수강 후기 접근이 막히던 구조 규명 및 복구
- **이력 초기화처럼 보인 매핑 오류** — 데이터가 사라진 것처럼 보였으나 **데이터는 살아 있고 연결만 어긋난 것**임을 확인해 원복으로 복구, 고객지원팀에 복구 방식 공유
- **외부 오류 제보 반증** — 자사 서버는 해당 응답 형식을 반환하지 않음을 실측으로 보여 원인이 사내 시스템이 아님을 규명

**품질 기반 구축**
- **결제 도메인 전수 테스트케이스 290건** — 레거시 결제 흐름을 문서로 지도화한 뒤, **과거 이슈 101건을 역매핑해 커버리지를 수치로 증명**
- **성능·부하 대응** — 정규 강의 시즌 트래픽 대비 부하 테스트 계획·실행·결과 보고, 인프라 증설 근거 제공
- **전사 성능 진단** — 웹 성능 점수 측정 후 저하 원인 9종을 정리하고, 실사용자 성능 데이터가 수집되지 않는 관측 공백을 별도로 지적
