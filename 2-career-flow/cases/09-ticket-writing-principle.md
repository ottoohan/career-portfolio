# 개발자가 첫 화면에서 이해하는 결함 티켓 — 피드백으로 바꾼 작성 규칙

**역할**: QA 티켓 작성 기준 수립
**한 줄**: "무엇이 문제고 무엇을 바라는지 모르겠다"는 개발자 피드백을 받고, 티켓 맨 위를 `문제`와 `기대 결과` 두 섹션으로 고정했다.

---

## 문제
- 사내 발송 콘솔 QA 티켓들이 현상·실측·추정·제안을 한 덩어리로 쓰고 있었다. 담당 개발자가 "무엇이 문제고 무엇을 바라는지 이해하기 힘들다"고 피드백했다.
- 같은 시기 QA 티켓 하나는 추정("전달 완료는 발송사 접수일 뿐")을 사실처럼 썼다. 개발자가 조사해 보니 발송사 결과 코드상 실제 도달이었고, 티켓은 철회됐다.

## 바꾼 규칙
```
## 문제        지금 무엇이 어떻게 되나. 1~3문장 + 재현 절차(환경·시각·경로·입력값) + 실제 결과(문구·수치 그대로)
## 기대 결과    고치면 무엇이 어떻게 되어야 하나. 확인 가능한 문장 ("X를 하면 Y가 보인다")
               정책 판단이 필요하면 "결정 필요: A / B"
---- 아래는 필요할 때만 ----
## 근거 → ## 원인 추정 (미확인) → ## 확인 요청 → ## 참고
```
- 제목은 `[영역] 무엇이 → 어떻게 잘못됨` 한 줄로 쓴다. 원인과 해결책은 제목에 넣지 않는다.
- 티켓 하나에 문제 하나만 담는다.
- 재확인 코멘트도 첫 줄에 판정(통과 / 미해결 / 부분)을 쓴다.
- 추정은 반드시 "추정·미확인"으로 표시하고 위 두 섹션에 넣지 않는다.

## 재사용할 원칙
- 티켓 독자는 개발자다. **문제와 기대 결과가 분리돼 있어야 "다 고쳤다"를 판정할 수 있다.**
- 추정을 사실처럼 쓰면 개발자가 엉뚱한 곳을 판다. 콘솔 표시가 틀렸다고 주장하기 전에 결과 코드나 실기기 수신으로 확인한다.
