# 페이지 이동 직전 분석 이벤트 유실 — "고쳤다"는 1차 수정을 다시 뒤집기

**역할**: 재발 탐지 · 근본 원인 재현 · 2차 수정 기준 제시
**상태**: 1차 수정 운영 반영, 2차 수정은 기준 제시 후 반영 대기 (2026.11 기준)
**한 줄**: 1차 수정이 배포된 다음 날에도 클릭 이벤트가 절반 넘게 유실되고 있었다. 원인은 SDK가 요청을 한 번에 하나씩만 보내는 구조였다.

---

## 문제
- 메시지 링크로 들어온 사용자를 중간 페이지에서 클릭 이벤트로 기록한 뒤 외부 채팅방으로 보내는 흐름이 있었다.
- 1차 수정으로 "SDK 내부 큐가 빌 때까지 최대 1.2초 대기 후 이동"을 넣었다.
- 다음 날 실제 발송에서 **채팅방 입장 수의 절반에도 못 미치는 클릭 이벤트만 기록**됐다. 다른 분석 도구에서도 외부 브라우저 도착 후 대부분이 유실되는 것으로 나왔다.

## 진단
1. 1차 수정의 검증은 "로컬에서 SDK 로드 지연 0~1000ms 통과"였다. **SDK 로드 지연만 흉내 냈고, 네트워크 왕복 시간과 전송 순서는 보지 않았다.**
2. SDK 소스를 읽어 보니 쓰고 있던 구버전 SDK는 기본 설정에서 **전송 중 플래그로 요청을 하나씩 직렬로 보내고**, 이탈용 전송(sendBeacon)을 쓰지 않았다.
3. 페이지 진입 시 식별·페이지뷰 이벤트가 1번 요청으로 먼저 나가면, 클릭 이벤트는 그 응답을 기다리는 2번 요청이 된다.
4. "큐가 비었다"는 SDK 내부 큐가 비었다는 뜻이지 서버 전송이 끝났다는 뜻이 아니다. 0.3초 뒤 이동하면 2번 요청이 `ERR_ABORTED`로 끊긴다.
5. 국내 → 해외 수집 서버의 콜드 연결은 1번 요청만 약 490ms였다. **운영 페이지에서 왕복 300ms 조건을 주자 유실이 재현됐다.**

## 조치
- 2차 수정 기준: 이동 조건을 "SDK 미전송 목록이 비었을 때(= 서버 200 수신)"로 바꾸고 상한은 약 3초.
- 검증 기준: 모바일 왕복 시간 재현 통과 → 운영 반영 → 다음 발송 전후의 입장 수 대비 클릭 비율 비교.

## 결과
- 1차 수정이 문제를 해결하지 못했다는 사실을 다음 날 실측으로 잡았다.
- 원인을 "타이밍 문제"라는 추상 수준이 아니라 **SDK 전송 구조와 네트워크 왕복 시간**까지 내려가 재현 가능한 형태로 만들었다.

## 재사용할 원칙
- 이탈 직전 트래킹은 **"서버 응답 완료"**를 판정 기준으로 삼는다. "큐 비움"이나 "함수 호출"은 기준이 아니다.
- 로컬 지연 테스트가 통과해도, 운영 네트워크 조건(콜드 연결·왕복 시간·직렬 큐)을 재현하지 않았다면 검증한 게 아니다.
- 이벤트 유실은 에러 없이 일어나는 조용한 실패다. 다른 원천(입장 수, 다른 분석 도구)과 교차 비교해야 보인다.
