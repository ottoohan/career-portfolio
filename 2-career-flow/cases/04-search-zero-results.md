# 고객 검색이 안 된다 — 원인 두 개가 겹친 결함

**역할**: 고객지원 제보 원인 진단 · 백엔드 직접 수정 · PR
**상태**: 운영 반영 (2026.10)
**한 줄**: 밑줄(`_`)이 들어간 이메일로 고객을 찾을 수 없다는 제보를 받았다. 파 보니 원인이 둘이었다. LIKE 와일드카드 때문에 결과가 틀렸고, 목록과 건수 쿼리의 검색 조건이 달라 총건수가 0으로 나왔다.

---

## 문제
- 고객지원팀이 백오피스 사용자 검색에서 `_`가 들어간 이메일을 입력하면 해당 고객을 찾을 수 없다고 제보했다.

## 진단 — 증상별 원인
| 증상 | 원인 | 영향 범위 |
|---|---|---|
| `_`가 들어간 이메일 검색 결과가 의도와 다름 | SQL LIKE에서 `_`는 "아무 글자 하나"라는 뜻이다. 이스케이프하지 않아 엉뚱한 고객이 섞이고 원하는 고객이 밀렸다 | `_` 포함 검색어 |
| 총건수가 0으로 나오고 페이지 이동이 사라짐 | 프론트엔드가 검색 타입 값을 바꾼 뒤, 목록 쿼리는 따라갔는데 **건수 쿼리만 옛 값을 받았다**. 새 값이 오면 조건이 `false`가 됐다 | 이메일 등 해당 검색 타입 전체. 약 9개월 전 변경 때부터 이 상태 |

- 제보 건은 두 증상이 겹쳐서 "찾을 수 없다"로 보였다.
- **운영 데이터로 볼 수 없는 것을 우회 검증**: 개인정보 열이 제거된 조회 환경이라 실제 이메일 매칭은 볼 수 없었다. 대신 `_`가 들어간 다른 식별자 열로 이스케이프 효과를 실측했다. 이스케이프 전후 결과가 수백 배 차이 났고, 이스케이프한 결과는 문자열 포함 검사 결과와 일치했다.

## 조치
- 목록·건수·엑셀이 같은 검색 조건 조각을 공유하도록 통합해서 다시 어긋날 수 없게 했다.
- LIKE 입력값 이스케이프와 `ESCAPE` 절을 추가했다.
- 첫 PR은 저장소의 브랜치 이름 규칙에 걸려 CI가 건너뛰어졌다. 규칙에 맞는 브랜치로 다시 올리고, 이 규칙을 내 작업 규칙서에 남겼다.

## 재사용할 원칙
- **목록과 건수가 따로 노는 구조**는 결함이 반복되는 자리다. 같은 조건을 두 군데 복사해 두지 말고 한 조각을 공유하게 한다.
- 한 제보 뒤에 원인이 여러 개 있을 수 있다. 증상을 나눠서 원인을 하나씩 대응시킨다.
- 운영 데이터에 직접 접근할 수 없으면, 같은 성질을 가진 다른 열로 **동작을 실측**한다.
