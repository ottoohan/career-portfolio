# 2,000건에서 조용히 잘리는 일괄 변경

**역할**: 운영 제보 원인 진단 · 데이터 보정 요청 · 근본 수정안
**상태**: 원인 규명 → 보정 방법·검증 기준 → 근본 수정안(프론트만 배포하면 되는 안) 제시까지 완료. 보정 실행은 백엔드 담당자에게 배정, 근본 수정은 개발 결정으로 인계 (2026.11)
**한 줄**: 수강기간을 일괄 연장했는데 대상의 약 3%가 빠졌다. 에러는 나지 않았다.

---

## 문제
- 운영자가 백오피스에서 한 상품의 수강생 수강기간을 일괄로 연장했다.
- 대상의 약 3%가 **기존 만료일 그대로** 남았다. 화면은 성공으로 끝났다.

## 진단
1. 프론트엔드가 목록을 아주 큰 페이지 크기로 한 번만 요청하고 있었다.
2. API 서버에 최대 페이지 크기 설정이 없어 **프레임워크 기본 상한 2,000**이 적용됐다.
3. 정렬이 최신순이라 **가장 먼저 등록한 수강생**이 잘렸다.
4. 저장은 화면에 보인 목록을 대상으로 했다. 화면에 안 보인 사람은 처음부터 저장 대상에 들어가지 않은 것이다.

## 조치
- 누락 대상의 식별 범위와 보정 방법을 티켓에 정리해 백엔드 담당자에게 배정했다.
- 근본 수정안: 프론트엔드가 상한 단위로 모든 페이지를 조회하도록 변경(프론트만 배포하면 됨).
- 검증 기준: 보정 후 "만료일별 인원" 조회 결과가 한 행, 전체 인원으로 나오는지 확인.

## 재사용할 원칙
- **"한 번에 다 가져온다"는 코드는 서버 상한을 만나면 조용히 잘린다.** 경계값 TC에는 항상 "프레임워크 기본 상한 + 1"을 넣는다.
- 일괄 작업 결과는 성공 메시지가 아니라 **대상 건수 = 반영 건수**로 판정한다.
