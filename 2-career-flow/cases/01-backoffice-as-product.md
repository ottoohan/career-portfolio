# 사내 백오피스를 프로덕트로 운영하기 — 만족도 8.23 → 9.33

**역할**: 백오피스 개선 KR 오너 (조사 설계 · 원인 진단 · 범위 분류 · 일부 직접 구현 · 배포 확인)
**기간**: 2025 하반기 ~ 2026
**한 줄**: 요청 처리 창구였던 사내 운영 도구에 사용자·지표·반복 사이클을 붙였다. 같은 사람들에게 같은 질문을 반복하며 수치 변화를 만들었다. 구현은 개발자들과 나눠 했다.

---

## 문제
- 운영 도구는 주인이 없었다. 요청이 오면 그때그때 고쳤고, 무엇이 나아졌는지 아무도 몰랐다.
- 운영자 불편은 "느리다", "또 틀렸다" 같은 감상으로만 전달됐고, 개발팀은 우선순위를 정할 근거가 없었다.

## 접근
1. **월간 만족도 조사를 고정 문항으로 정착** — 문항을 바꾸지 않아야 회차 간 비교가 된다.
2. **의견마다 코드에서 원인을 확인한 뒤 구현 범위를 3단계로 분류**
   | 범위 | 정의 | 처리 |
   |---|---|---|
   | A | 프론트엔드 단독 | 직접 구현 · 배포 |
   | B | 서버 로직 변경, 스키마 변경 없음 | 개발자와 함께 |
   | C | 스키마 변경 필요 | 백엔드 팀에 요청 티켓 |
   데이터베이스 쓰기 권한이 없다는 제약을 전제로 둔 분류다. "누가 할 수 있는가"가 먼저 정해지니 일정 약속이 정확해졌다.
3. **"이미 있는 기능"을 먼저 가려냄** — 4회차 조사 의견을 보면 상당수가 이미 배포된 기능이었다(재수강 여부 엑셀 열, 다중 상품 검색 등). 개발 없이 안내만으로 해결했다.
4. **위험도 순으로 배치** — 운영자 체감이 크고 회귀 위험이 작은 것부터 한다. 가격·결제처럼 영향이 큰 변경은 결제 회귀 TC를 붙이는 조건으로만 진행했다.

## 원인 진단 예시 (직접 고친 것)
- **목록 시각의 분 자리에 월이 찍힘**: 쓰던 날짜 포맷 라이브러리는 흔한 라이브러리와 반대로 `mm`이 월, `MM`이 분이었다. 분 자리에 `mm`을 써서 월이 찍혔다. 저장값은 정상이고 표시만 틀렸다. 2줄 수정 + 단위 테스트 3건.
- **"복제" 버튼이 몇 년째 동작하지 않음**: 버튼 핸들러가 빈 함수로 남아 있었다. 상세 조회 → 식별자·작성자 필드 제거 → 등록 폼 미리 채우기로 프론트엔드 단독 구현.
- **새 항목이 항상 맨 아래 챕터로 들어감**: 부모를 "마지막 챕터"로 고정하는 함수가 원인이었다. 소속 챕터 선택 UI를 일반화해서 해결.
- **동시 편집 충돌**: 저장 방식을 확인하고, 프론트 단계 방어와 서버 단계 방어를 나눠 개선안으로 제안했다.

## 결과
| 지표 | 전 | 후 | 비고 |
|---|---|---|---|
| 운영자 만족도 (사내 월간 조사, 10점 척도) | 8.23 (4월, 26명) | **9.33** (10월 최종 회차, 15명) | 6회 누적 114건 · 고유 31명. 6월(7.75)·9월(8.65)에 한 번씩 내려갔다 |
| 백오피스 개선 PR 머지 (KR 집계, 반기 대비) | 25 | **49** (+96%) | 개발자들과 함께 낸 팀 합계 |

- 장기 과제였던 예약·일괄 업로드가 배포된 다음 회차에는 해당 항목이 불만이 아니라 칭찬 코멘트로 돌아왔다.
- 내 몫은 KR 설계, 조사 운영, 의견별 원인 진단과 범위 분류, 범위 A 직접 구현, 배포 확인이다.

## 재사용할 원칙
- 내부 도구도 사용자가 있으면 프로덕트다. 지표 없이 개선하면 개선했다는 주장만 남는다.
- 요청을 받으면 **"이미 있나 → 누가 할 수 있나(A/B/C) → 위험한가"** 순서로 거른다.
- 진단은 코드 라인까지 내려가야 범위 분류가 정확해진다.
