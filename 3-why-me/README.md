# 내가 가져가는 것

> 지원 직무: **QA + 운영지원(Product Operations)** — 품질 검증과, 운영자가 쓰는 도구·운영 문의 대응을 한 사람이 이어서 맡는 자리.

> **문제를 발견하면 원인을 코드에서 찾고, 고칠 수 있는 건 직접 고치고, 운영에서 다시 잽니다. 제 권한 밖의 일은 결정할 것을 A/B로 만들어 담당자와 닫습니다.**
> 이 전 과정을 AI 에이전트 위에 규칙·검증·측정 구조로 올려, 혼자서도 여러 직군의 일을 안전하게 돌립니다.

---

## 1. 일하는 방식

### 1-1. 역할 경계에서 멈추지 않습니다 — 발견부터 재발 방지까지

```
발견(QA·VOC) → 원인(코드·쿼리·로그) → 결정 요청(기획) → 수정(FE·BE) → 배포 확인 → 운영 실측 → 재발 방지 규칙
```

| 사례 | 이 흐름에서 직접 한 구간 | 결과 |
|---|---|---|
| [고객 검색 결함](../2-career-flow/cases/04-search-zero-results.md) | 고객지원 제보 → SQL 원인 2개 → 백엔드 직접 수정 → 개인정보가 빠진 조회 환경에서 다른 열로 동작 실측 | 운영 반영 |
| [백오피스 만족도](../2-career-flow/cases/01-backoffice-as-product.md) | 조사 설계 → 의견별 코드 원인 → 범위 A/B/C 분류 → 범위 A 직접 구현, 나머지는 개발자들과 | 8.23 → 9.33 (10점 척도, 월간 6회 · 최종 15명 응답) |
| [2,000건 잘림](../2-career-flow/cases/05-silent-2000-cap.md) | 운영 제보 → 서버 기본 상한 진단 → 보정 방법과 검증 기준 → 경계값 TC 규칙화 | 원인·보정안까지 내 몫 완료, 근본 수정은 개발 결정으로 인계 |
| [폴백 은폐 사고](../2-career-flow/cases/07-fallback-masked-as-success.md) | 사고 회고 → "QA도 그 경로를 TC에 넣지 않았다" 인정 → TC 설계 기준 4묶음 → 2차 QA에 적용 | 2차 QA 진행 중: 43건 중 35건 수행(통과 29·실패 6), 8건 미수행 |

**규모**: 숫자는 [경력기술서 핵심 결과](../2-career-flow/경력기술서.md#핵심-결과) 한 곳에 모아 두었다.

### 1-2. 숫자를 다루는 방식

| 원칙 | 실제로 한 일 |
|---|---|
| AI 판정은 사람이 표본으로 확인한다 | 운영 실수 분류 무작위 20건을 직접 검수해 20/20 일치. AI 판정을 보면서 한 검수라 "독립 검증 아님"까지 함께 적음 |
| 내 계산도 다시 잰다 | 크리티컬 유출률 첫 보고(3.40%)의 분모 결함을 하반기 재측정에서 찾아 고치고, 고친 값(상반기 1.09%·하반기 1.52%)과 함께 "반기 차이는 표본이 작아 판별 불가"까지 실음 |
| 내가 안 잰 건 내 숫자라고 안 한다 | 벤치마크 −52%는 "동료 측정, 단일 태스크 3회 시행 파일럿"으로 표기. 공용 TC 도구는 "초기 버전 설계, 이후 동료가 확장", E2E는 "동료가 도입한 기반 위에 36건 자동화" |
| 기준을 못 넘으면 인용하지 않는다 | AI 채점자-사람 일치율이 목표 85% 미달이라 "검증 중"으로 둠. 검증 절차가 흔들린 표본 10건은 산입 보류 |
| 내 도구의 결함도 공개하고 고친다 | 이 포트폴리오를 공개한 뒤 독립 검토에서 ① 측정 스크립트의 거부 오탐·기간 기준 문제 ② push 훅의 `eval`·명령 치환 우회가 나왔다. 둘 다 고치고 테스트를 늘렸다(28 → 38개). 측정은 다시 재서 "교정·거부가 늘었다"던 이전 서술을 철회했다([AI 부록 4절](ai-appendix.md)) |
| "0건"을 바로 믿지 않는다 | 실시간 조회 DB가 40분 멈춘 걸 모르고 "0행"이라 판정했다가 철회 → 최신성 검사를 도구에 넣음 |

### 1-3. AI가 틀린 기록과 그 뒤 바꾼 규칙

AI에게 일을 맡기면 틀린다. 틀린 걸 누가 어떻게 잡았는지, 그 뒤 무엇을 바꿨는지를 남겼다.

| AI가 틀린 것 | 누가·어떻게 잡았나 | 그 뒤 바꾼 것 |
|---|---|---|
| 한 달 교정 40여 건, 대부분 기준 오해("누적 말고 월별", "메인 말고 베스트") | 내가 첫 결과물에서 기준이 틀린 걸 지적 | 조회·산출 전 첫 줄에 기준 가정을 먼저 쓰는 규칙 |
| 고객 안내 문구에 외부 메신저 앱 메뉴 경로를 두 번 틀리게 씀(기억 → 공식 도움말, 둘 다 실제 앱과 다름) | 내가 실기기 화면으로 확인 | 최근 출처 2곳 + 실기기 확인 전에는 문구를 배포하지 않음 |
| QA 중 편의·표기 수준 관찰 3건을 결함 티켓으로 등록 | 내가 출시 차단 사유가 아니라고 판단해 non-issue 처리 | 데이터 손상·실고객 노출·조용한 실패가 아니면 "관찰"로 보고, 티켓화는 사람이 정함 |
| 결함 티켓에 추정을 사실처럼 씀 | 담당 개발자가 조사 후 반박 | 티켓 맨 위는 문제 / 기대 결과, 추정은 "미확인" 섹션으로 → [사례 09](../2-career-flow/cases/09-ticket-writing-principle.md) |
| 조회 DB 갱신이 멈춘 걸 모르고 "0건"이라 판정 | 갱신 시각 대조로 철회 | 조회 래퍼에 최신성 검사 |
| RAG 실험의 사람 판정 일부가 AI 판정을 본 뒤 수정됨 | 내가 절차 오염으로 판단 | 더 좋아 보이는 수치를 산입하지 않고 "검증 중"으로 → [사례 10](../2-career-flow/cases/10-rag-evaluation.md) |

### 1-4. AI는 이렇게 씁니다

AI 에이전트 위에 규칙·검증·측정 구조를 세워 원인 진단부터 배포 확인까지 한 흐름으로 돌렸고, AI가 만든 결과(TC 생성·RAG 답변·추천 점수)가 맞는지 재는 일도 맡았다. 지원 직무의 중심은 QA와 운영지원이라 자세한 내용은 부록으로 뺐다 → [부록 — AI 업무 환경과 AI 결과물 평가](ai-appendix.md)

## 2. 합류하면 첫 90일

| 기간 | 할 일 | 산출물 |
|---|---|---|
| 1~2주 | 레포·환경·배포 지도, 규칙서와 push 훅 셋업, 지원 채널 4주치 분류 | 환경 ↔ 브랜치 표, 인입 유형별 비율 |
| 3~6주 | 핵심 매출 경로 TC와 회귀 세트, 크리티컬 유출률 정의(분자·분모) 합의 | TC + 첫 기준선 |
| 7~10주 | 반복 업무 3개를 스킬화, 조회 래퍼, 독립 검증 에이전트를 팀 완료 정의에 제안 | 팀이 쓰는 도구 3개 |
| 11~13주 | 같은 지표 재측정, 개선 효과와 미달 보고 | 전후 비교 보고서 |
