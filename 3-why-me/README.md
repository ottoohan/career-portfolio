# 왜 이 사람이 필요한가

> **문제를 발견한 사람이 원인을 코드에서 찾고, 고칠 수 있는 건 직접 고치고, 운영에서 다시 잰다. 내 권한 밖은 결정할 것을 A/B로 만들어 담당자와 닫는다.**
> 그 전 과정을 AI 에이전트 위에 규칙·검증·측정 구조로 올려서, 혼자서도 여러 직군의 일을 안전하게 돌린다.

---

## 1. 세 가지 주장과 근거

### A. 역할 경계에서 멈추지 않는다 — 발견부터 재발 방지까지 이어서 맡는다

```
발견(QA·VOC) → 원인(코드·쿼리·로그) → 결정 요청(기획) → 수정(FE·BE) → 배포 확인 → 운영 실측 → 재발 방지 규칙
```

| 사례 | 이 흐름에서 직접 한 구간 | 상태 |
|---|---|---|
| [고객 검색 결함](../2-career-flow/cases/04-search-zero-results.md) | 고객지원 제보 → SQL 원인 2개 → 백엔드 직접 수정 → 개인정보가 빠진 조회 환경에서 다른 열로 동작 실측 | 운영 반영 |
| [2,000건 잘림](../2-career-flow/cases/05-silent-2000-cap.md) | 운영 제보 → 서버 기본 상한 진단 → 보정 방법과 검증 기준 → 경계값 TC 규칙화 | 보정 배정, 근본 수정 결정 대기 |
| [폴백 은폐 사고](../2-career-flow/cases/07-fallback-masked-as-success.md) | 사고 회고 → "QA도 그 경로를 TC에 넣지 않았다" 인정 → TC 설계 기준 4묶음 → 내 TC 규칙에 반영 | 2차 TC 설계 완료 |
| [백오피스 만족도](../2-career-flow/cases/01-backoffice-as-product.md) | 조사 설계 → 의견별 코드 원인 → 범위 A/B/C 분류 → 범위 A 직접 구현, 나머지는 개발자들과 → 7.29→8.82 | 완료 |

**규모**: 2026년 프로덕션 레포 커밋 328건(6개 레포, 개발 직군이 아닌 상태), PRD 12건+, 본인 등록 이슈 티켓 3,316건, QA 챕터 검증 1,136건(팀 합산).

### B. AI를 "질문 도구"가 아니라 "업무 시스템"으로 운영한다

AI 활용을 다섯 단계로 나누면, 이 사람은 4~5단계에서 일한다.

| 단계 | 정의 | 근거 |
|---|---|---|
| L1 질의응답 | 모르는 걸 묻는다 | — |
| L2 생성 | 코드·문서 초안을 AI로 만든다 | AI로 작성하고 원인 진단·검증·배포 확인은 직접 맡은 커밋 328건, PRD·정책서·와이어프레임 |
| L3 도구화 | 반복 업무를 스킬·스크립트로 고정한다 | 문의 원인 판정 스킬(도입 1주에 11회 사용), 휴먼에러 집계 스킬, 읽기 전용 조회 래퍼(키 비노출·쓰기 차단·최신성 검사) |
| **L4 하네스 운영** | 규칙·기억·검증·안전장치를 구조로 만든다 | 규칙서 240줄(완료 정의·절대 금지·기준 먼저 출력), 메모리 250여 개 파일 + 교차 버그 패턴 10개, **구현자 설명 없이 반박하는 독립 검증 에이전트**, 복구 불가 동작만 막는 훅(28개 입력 테스트), 금요일 자동 집계 루틴, 무인 장기 실행 규칙 |
| **L5 측정·평가** | AI 사용과 AI 결과물을 숫자로 평가하고 고친다 | 세션 로그 201개 실측 → 개선 7건 → 같은 스크립트로 재측정([4절](#4-측정으로-개선한다)), **RAG 평가 실험 설계·AI 채점자 보정**([5절](#5-rag-평가-실험--ai-결과물을-재는-법)), 사내 AI 개발 프레임워크 QA 트랙 목표·측정 관리 |

이 구조 전체를 다른 회사로 옮기는 방법을 [1-ai-workflow-guide](../1-ai-workflow-guide/README.md)에 정리했다. 템플릿·훅·측정 스크립트가 들어 있다.

### C. 이 사람이 낸 숫자는 믿어도 된다

AI로 일을 빨리 하는 사람은 많다. 그 결과를 **믿을 수 있게 만드는 사람**은 드물다.

| 원칙 | 실제로 한 일 |
|---|---|
| 미달도 싣는다 | 결함 유출률 3.40%(목표 2%), 무사고 배포율 96.60%(목표 98%)를 그대로 보고 |
| 내가 안 잰 건 내 숫자라고 안 한다 | 벤치마크 −52%는 "동료 측정, 단일 태스크 3회 시행 파일럿"으로 표기. 공용 TC 도구는 "초기 버전 설계, 이후 동료가 확장", E2E는 "동료가 도입한 기반 위에 36건 자동화"로 정정 |
| 기준을 못 넘으면 인용하지 않는다 | AI 채점자-사람 일치율이 목표 85%에 못 미쳐 "검증 중"으로 둠. 검증 절차가 흔들린 표본 10건은 산입 보류 |
| 나빠진 것도 보고한다 | 하네스 개선 1주 중간 측정에서 교정률·권한 거부가 오히려 늘었다는 사실을 그대로 기록 |
| "0건"을 바로 믿지 않는다 | 실시간 조회 DB가 40분 멈춘 걸 모르고 "0행"이라 판정했다가 철회 → 최신성 검사를 도구에 넣음 |

## 2. AI로 바꾼 일하는 방식 — 전과 후

| 업무 | 전 | 후 |
|---|---|---|
| 운영 문의 원인 파악 | 매번 설명부터 다시 | 스킬 하나로 "원인 / 시스템 vs 휴먼에러 / 운영 조치 가능 여부" 형식 고정 |
| 데이터 조회 | 즉석 스크립트 한 달 400회 이상, 키 노출 위험 | 읽기 전용 래퍼 하나. 쓰기 차단, 실행 시각·최신성 표기 |
| 지표 요청 | "누적 말고 월별" 같은 교정 반복 | 첫 줄에 기준 가정을 먼저 보여 주고 진행 → 틀리면 그 줄에서 잡힘 (효과는 아직 수치로 확인 안 됨, 4절) |
| 코드 수정 완료 판단 | 구현한 쪽이 "됐다"고 판단 | 독립 검증 에이전트의 차단 0건 + 배포 환경 URL이 있어야 완료 |
| 주간 휴먼에러 집계 | 사람이 매주 요청 | 금요일 17시 자동 루틴이 DM으로 보냄 |
| 여러 레포에 걸친 작업 | 한 세션에서 순서대로 | 레포별 워크트리 + 병렬 에이전트, API 계약을 먼저 고정 |
| TC 작성 | 사람 3시간 42분 | AI 스킬 1시간 47분(−52%) [동료 측정, 파일럿] |

## 4. 측정으로 개선한다

**기준선을 재고 → 바꾸고 → 같은 스크립트로 다시 잰다.**

| 문제 (기준선 10/1~11/3) | 바꾼 것 |
|---|---|
| 교정 41건(약 4%), 대부분 기준 오해 | 규칙서에 "기준 먼저 출력" |
| 즉석 조회 스크립트 400회 이상 | 읽기 전용 조회 래퍼 |
| 권한 거부 62건, 그중 자격증명 탐색 12건 이상 | 자격증명 폴더 탐색 deny, 키는 래퍼 안에서만 |
| 가장 많은 업무(문의 원인 파악 84건)에 스킬 없음 | 문의 원인 판정 스킬, 휴먼에러 집계 스킬 |
| 300분 이상 세션 36개 | 1세션 1티켓 + PROGRESS.md 규칙 |
| 구현자 자기 검증 | 독립 검증 에이전트를 완료 정의에 포함 |
| 정기 집계 수동 요청 | 금요일 자동 루틴 |

**1주 중간 측정** — 공개한 [`session_metrics.py`](../1-ai-workflow-guide/templates/scripts/session_metrics.py)로 두 구간을 같은 방식으로 다시 쟀다. 처음 측정에 쓴 스크립트와 같은 구간에서 숫자가 일치하는 것을 확인했다.

| 지표 | 개선 전 (10/1~11/3, 154세션) | 1주 후 (11/4~11/11, 60세션) | 판정 |
|---|---|---|---|
| 세션당 스킬 호출 | 0.10회 | **0.32회** | 개선 |
| 교정률 | 3.7% | 5.1% | 개선 안 됨 |
| 세션당 권한 거부 | 0.22건 | 0.45건 | 악화 |
| 300분 초과 세션 비율 | 17% | 27% | 악화 |

- 개선 전 구간이 처음 측정(201세션)보다 적은 이유: 기간을 파일 수정 시각으로 자르는데, 10월 세션 일부를 11월에 이어서 썼다.
- 해석(추정): 교정 탐지는 교정 표현이 발화 앞 80자 안에 있으면 세는 키워드 방식이라 오탐이 섞인다. 이 주에는 발표 자료처럼 긴 작업이 몰렸다.
- 본 측정은 한 달 뒤 같은 스크립트로 한다. **나빠진 숫자를 숨기지 않고 다음 개선 대상으로 둔다.**

## 5. RAG 평가 실험 — AI 결과물을 재는 법

사내 RAG 스터디 4부 "RAG 평가"(11/11)를 맡아 발표 전에 직접 실험했다.

| 설계 | 내용 |
|---|---|
| 코퍼스 | 사내 위키 문서 수백 개 |
| 골든셋 | 40문항(사실 20 · 여러 문서 종합 8 · 답 없음 8 · 혼동 유도 4), 정답은 any-of / all-of 그룹 |
| 비교 | 단어 단위 BM25 / 바이그램 BM25 / 정답 문서를 직접 준 경우(오라클). 생성 모델과 채점 모델은 분리 |
| 실제 질문 | 지원 채널 실제 질문 160여 개 |

| 결과 | 값 | 의미 |
|---|---|---|
| 합격 문항 | 단어 21/40 · 바이그램 22/40 · **오라클 35/40** | 병목은 답을 만드는 쪽이 아니라 **찾는 쪽** |
| 3회 반복 | 다수결 25/40, 흔들림 5~7% | 한 번 실행으로 판정하면 안 된다 |
| 파일 단위 Recall | 합격을 예측하지 못함 | 정답 단락이 들어왔는지로 재야 한다 |
| 실제 질문의 위키 커버리지 | 약 5분의 1 (AI 초벌 라벨 기준) | 검색을 고치기 전에 문서가 없다 |
| 실제 질문 Recall | 0.77 → 0.53 | 골든셋 점수는 실사용보다 낙관적 |
| AI 채점자 보정 | 사람 판정 25건 기준 합격 일치 0.58 → 0.83, 불합격 일치 0.92 | 목표 85%에 미달이라 **"검증 중"** |

청중이 개발·기획·QA가 섞인 12명이라, 본편은 쉬운 말로 쓰고 깊은 내용은 발표자 교재로 분리했다.

## 6. 합류하면 첫 90일

| 기간 | 할 일 | 산출물 |
|---|---|---|
| 1~2주 | 레포·환경·배포 지도, 규칙서와 push 훅 셋업, 지원 채널 4주치 분류 | 환경 ↔ 브랜치 표, 인입 유형별 비율 |
| 3~6주 | 핵심 매출 경로 TC와 회귀 세트, 결함 유출률 정의 합의 | TC + 첫 기준선 |
| 7~10주 | 반복 업무 3개를 스킬화, 조회 래퍼, 독립 검증 에이전트를 팀 완료 정의에 제안 | 팀이 쓰는 도구 3개 |
| 11~13주 | 같은 지표 재측정, 개선 효과와 미달 보고 | 전후 비교 보고서 |
