# 내가 가져가는 것

> 지원 직무: **QA + 운영지원(Product Operations)** — 품질 검증과, 운영자가 쓰는 도구·운영 문의 대응을 한 사람이 이어서 맡는 자리.

> **문제를 발견하면 원인을 코드에서 찾고, 고칠 수 있는 건 직접 고치고, 운영에서 다시 잽니다. 제 권한 밖의 일은 결정할 것을 A/B로 만들어 담당자와 닫습니다.**
> 이 전 과정을 AI 에이전트 위에 규칙·검증·측정 구조로 올려, 혼자서도 여러 직군의 일을 안전하게 돌립니다.

---

## 1. 세 가지

### A. 역할 경계에서 멈추지 않습니다 — 발견부터 재발 방지까지

```
발견(QA·VOC) → 원인(코드·쿼리·로그) → 결정 요청(기획) → 수정(FE·BE) → 배포 확인 → 운영 실측 → 재발 방지 규칙
```

| 사례 | 이 흐름에서 직접 한 구간 | 결과 |
|---|---|---|
| [고객 검색 결함](../2-career-flow/cases/04-search-zero-results.md) | 고객지원 제보 → SQL 원인 2개 → 백엔드 직접 수정 → 개인정보가 빠진 조회 환경에서 다른 열로 동작 실측 | 운영 반영 |
| [백오피스 만족도](../2-career-flow/cases/01-backoffice-as-product.md) | 조사 설계 → 의견별 코드 원인 → 범위 A/B/C 분류 → 범위 A 직접 구현, 나머지는 개발자들과 | 7.29 → 9.4 (10점 척도, 내부 어드민 사용자 약 50명 응답) |
| [2,000건 잘림](../2-career-flow/cases/05-silent-2000-cap.md) | 운영 제보 → 서버 기본 상한 진단 → 보정 방법과 검증 기준 → 경계값 TC 규칙화 | 원인·보정안까지 내 몫 완료, 근본 수정은 개발 결정으로 인계 |
| [폴백 은폐 사고](../2-career-flow/cases/07-fallback-masked-as-success.md) | 사고 회고 → "QA도 그 경로를 TC에 넣지 않았다" 인정 → TC 설계 기준 4묶음 → 2차 QA에 적용 | 2차 QA 43건 수행 중(통과 29·실패 6·미수행 8) |

**규모**: 2026년 프로덕션 레포 직접 커밋 328건(6개 레포), PRD 12건+, 본인 등록 이슈 티켓 3,316건(재직 누적), QA 챕터 검증 1,136건(3개 스쿼드 팀 합산, 2026 상반기).

### B. AI를 "질문 도구"가 아니라 "업무 시스템"으로 운영합니다

AI 활용을 다섯 단계로 나눠, 단계마다 제가 실제로 한 일을 적었습니다. 단계 구분은 제 기준이고, 판단은 근거 열로 해 주세요.

| 단계 | 정의 | 근거 |
|---|---|---|
| L1 질의응답 | 모르는 걸 묻는다 | — |
| L2 생성 | 코드·문서 초안을 AI로 만든다 | 커밋 328건 — 코드 작성은 AI, 원인 진단·검증·배포 확인은 제가. main 머지는 사람이 승인하는 관문으로 둠 |
| L3 도구화 | 반복 업무를 스킬·스크립트로 고정한다 | 문의 원인 판정 스킬(도입 1주에 11회 사용), 휴먼에러 집계 스킬, 읽기 전용 조회 래퍼(키 비노출·쓰기 차단·최신성 검사) |
| **L4 하네스 운영** | 규칙·기억·검증·안전장치를 구조로 만든다 | 규칙서 241줄 · 메모리 248개 파일(11/12 실측, 회사 내용이라 비공개 — 일반화한 뼈대는 [템플릿](../1-ai-workflow-guide/templates/)), 교차 버그 패턴 10개, 복구 불가 동작만 막는 훅(38개 입력 테스트), 금요일 자동 집계 루틴. **독립 검증 에이전트**: 11/3~11/12 변경 13건에 실행, 차단 1건(배포 순서 위반 시 운영 400), 같은 기능 1차 검증에서 차단 1건(중복 판정 반례), 확인 필요·주의 20여 건 |
| **L5 측정·평가** | AI 사용과 AI 결과물을 숫자로 평가하고 고친다 | 세션 로그 실측 → 개선 7건 → 같은 스크립트로 재측정([4절](#4-측정으로-개선한다)), **RAG 평가 실험 설계·AI 채점자 보정**([5절](#5-rag-평가-실험--ai-결과물을-재는-법)), 사내 AI 개발 프레임워크 QA 트랙 목표·측정 관리 |

이 구조를 다른 회사로 옮기는 방법은 [1-ai-workflow-guide](../1-ai-workflow-guide/README.md)에 있습니다. 템플릿·훅·측정 스크립트가 들어 있습니다.

### C. 숫자를 다루는 방식

| 원칙 | 실제로 한 일 |
|---|---|
| 미달도 싣는다 | 결함 유출률 3.40%(목표 2%)를 그대로 보고 |
| 내가 안 잰 건 내 숫자라고 안 한다 | 벤치마크 −52%는 "동료 측정, 단일 태스크 3회 시행 파일럿"으로 표기. 공용 TC 도구는 "초기 버전 설계, 이후 동료가 확장", E2E는 "동료가 도입한 기반 위에 36건 자동화" |
| 기준을 못 넘으면 인용하지 않는다 | AI 채점자-사람 일치율이 목표 85% 미달이라 "검증 중"으로 둠. 검증 절차가 흔들린 표본 10건은 산입 보류 |
| 내 도구의 결함도 공개하고 고친다 | 이 포트폴리오를 공개한 뒤 독립 검토에서 ① 측정 스크립트의 거부 오탐·기간 기준 문제 ② push 훅의 `eval`·명령 치환 우회가 나왔다. 둘 다 고치고 테스트를 늘렸다(28 → 38개). 측정은 다시 재서 "교정·거부가 늘었다"던 이전 서술을 철회했다(4절) |
| "0건"을 바로 믿지 않는다 | 실시간 조회 DB가 40분 멈춘 걸 모르고 "0행"이라 판정했다가 철회 → 최신성 검사를 도구에 넣음 |

## 2. AI로 바꾼 일하는 방식 — 전과 후

| 업무 | 전 | 후 |
|---|---|---|
| 운영 문의 원인 파악 | 매번 설명부터 다시 | 스킬 하나로 "원인 / 시스템 vs 휴먼에러 / 운영 조치 가능 여부" 형식 고정 |
| 데이터 조회 | 즉석 스크립트 한 달 400회 이상, 키 노출 위험 | 읽기 전용 래퍼 하나. 쓰기 차단, 실행 시각·최신성 표기 |
| 지표 요청 | "누적 말고 월별" 같은 교정 반복 | 첫 줄에 기준 가정을 먼저 보여 주고 진행 → 틀리면 그 줄에서 잡힘 |
| 코드 수정 완료 판단 | 구현한 쪽이 "됐다"고 판단 | 독립 검증 에이전트의 차단 0건 + 배포 환경 URL이 있어야 완료 |
| 주간 휴먼에러 집계 | 사람이 매주 요청 | 금요일 17시 자동 루틴이 DM으로 보냄 |
| 여러 레포에 걸친 작업 | 한 세션에서 순서대로 | 레포별 워크트리 + 병렬 에이전트, API 계약을 먼저 고정 |

> TC 작성 시간 −52%(사람 3시간 42분 → AI 스킬 1시간 47분)는 동료가 단일 태스크 3회로 잰 파일럿이라 위 표에 넣지 않았다.

## 4. 측정으로 개선한다

**기준선을 재고 → 바꾸고 → 같은 스크립트로 다시 잰다.**

| 문제 (11/3 1차 진단) | 바꾼 것 |
|---|---|
| 교정 40여 건, 대부분 기준 오해("누적 말고 월별") | 규칙서에 "기준 먼저 출력" |
| 즉석 조회 스크립트 400회 이상 | 읽기 전용 조회 래퍼 |
| 자격증명 폴더 탐색이 거부된 사례 12건 이상 | 자격증명 폴더 탐색 deny, 키는 래퍼 안에서만 |
| 가장 많은 업무(문의 원인 파악 84건)에 스킬 없음 | 문의 원인 판정 스킬, 휴먼에러 집계 스킬 |
| 300분 이상 세션이 잦음 | 1세션 1티켓 + PROGRESS.md 규칙 |
| 구현자 자기 검증 | 독립 검증 에이전트를 완료 정의에 포함 |
| 정기 집계 수동 요청 | 금요일 자동 루틴 |

**1주 중간 측정** — 공개한 [`session_metrics.py`](../1-ai-workflow-guide/templates/scripts/session_metrics.py)로 두 구간을 같은 방식으로 쟀다. 기간은 세션 시작 시각(KST) 기준이라 다시 돌려도 같은 값이 나온다.

| 지표 | 개선 전 (10/1~11/3, 150세션) | 1주 후 (11/4~11/11, 56세션) | 판정 |
|---|---|---|---|
| 세션당 스킬 호출 | 0.11회 (16회) | **0.36회** (20회) | 개선 (절대 건수 작음) |
| 교정 비율 | 4.4% | 3.1% | 개선 신호 (표본 작음) |
| 세션당 권한 거부 | 0.11건 | 0.05건 | 개선 신호 (표본 작음) |
| 300분 초과 세션 비율 | 20% | 27% | 악화 |

- **측정 방식 정정(11/12)**: 처음 공개한 수치(교정 3.7→5.1%, 거부 0.22→0.45건)는 ① 도구 결과 본문 어디에든 "rejected"가 있으면 거부로 세고 ② 기간을 파일 수정 시각으로 잘라 세션을 다시 열면 구간이 바뀌는 문제가 있었다. 고친 뒤 다시 잰 값이 위 표다. 스킬 호출 개선은 두 방식 모두에서 유지된다.
- 교정 탐지는 교정 표현이 발화 앞 80자 안에 있으면 세는 키워드 방식이라 오탐이 섞인다. 1주 구간은 56세션이라 교정·거부 차이는 아직 결론으로 쓰지 않는다.
- 장시간 세션은 늘었다. 이 주에 발표 자료처럼 긴 작업이 몰렸다(추정). 다음 개선 대상으로 둔다.

## 5. RAG 평가 실험 — AI 결과물을 재는 법

사내 RAG 스터디 4부 "RAG 평가"(11/11)를 맡아 발표 전에 직접 실험했다.

| 설계 | 내용 |
|---|---|
| 코퍼스 | 사내 위키 문서 수백 개 |
| 골든셋 | 40문항(사실 20 · 여러 문서 종합 8 · 답 없음 8 · 혼동 유도 4), 정답은 any-of / all-of 그룹 |
| 비교 | 단어 단위 BM25 / 바이그램 BM25 / 정답 문서를 직접 준 경우(오라클). 생성 모델과 채점 모델은 분리 |
| 반복 | 조건마다 3회 실행, 문항별 다수결 |
| 실제 질문 | 지원 채널 실제 질문 160여 개 |

| 결과 | 값 | 의미 |
|---|---|---|
| 합격 문항 (3회 다수결) | 단어 22/40 · 바이그램 25/40 · **오라클 36/40** | 병목은 답을 만드는 쪽이 아니라 **찾는 쪽**. 바이그램 vs 오라클 차이는 유의(정확 McNemar 검정 p=0.001), 단어 vs 바이그램은 유의하지 않음(p=0.51) |
| 흔들림 | 5~10% (3회 중 판정이 갈린 문항 비율) | 한 번 실행으로 판정하면 안 된다 |
| 파일 단위 Recall | 합격을 예측하지 못함 | 정답 **단락**이 들어왔는지로 재야 한다 |
| 실제 질문의 위키 커버리지 | 21% (AI 초벌 라벨 기준) | 검색을 고치기 전에 문서가 없다 |
| Recall: 골든셋 vs 실제 질문 | 0.77 vs 0.53 | 골든셋 점수는 실사용보다 낙관적 |
| AI 채점자 보정 | 사람 판정 25건 기준 합격 일치 0.58 → 0.83, 불합격 일치 0.92 | 기준을 **같은 25건으로 다듬은 값**이라 과적합 가능성이 있다. 판정자를 숨긴 새 표본으로 다시 재기 전까지 **"검증 중"** |

청중이 개발·기획·QA가 섞인 12명이라, 본편은 쉬운 말로 쓰고 깊은 내용은 발표자 교재로 분리했다.
