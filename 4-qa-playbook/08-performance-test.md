# 08. 성능·부하 테스트

> "느리다"는 판정이 아니다. **목표 수치를 먼저 정하고**, 운영과 같은 요청 비율로 밀어서, 목표를 넘는지만 본다.

## 언제 하나
- 수강 신청·한정 판매처럼 **트래픽이 짧은 시간에 몰리는 시즌 전** (전 직장에서는 정규 강의 오픈 시즌마다)
- 캐시·쿼리·인프라 구성이 바뀐 뒤
- "운영에서 느려졌다"는 제보가 반복될 때 — 먼저 운영 지표(APM)로 어디가 느린지 본 다음

## 템플릿 — 테스트 계획 (1장)

| 항목 | 작성 |
|---|---|
| 목적 | 예: 시즌 오픈 직후 10분간 신청·결제 경로가 버티는지 |
| 대상 경로 | 상세 조회 → 신청 → 결제 생성 → 완료 (매출 경로부터) |
| 부하 모델 | 지난 시즌 최고 분당 요청 수 × 여유 배수(예: 1.5배), **경로별 비율은 운영 로그 그대로** |
| 성공 기준 | p95 응답 시간 · 에러율 · 결제 성공률의 목표값 (숫자로) |
| 환경 | 운영과 같은 사양인가, 외부 결제·발송은 모의로 대체했나(대체했으면 그 사실을 결과에 적는다) |
| 데이터 | 실제와 비슷한 양의 상품·회원·주문 (빈 DB는 빠르다) |
| 중단 기준 | 에러율 급증, 공유 환경의 다른 팀 영향 |
| 담당 | 시나리오(QA) · 인프라 지표(개발·인프라) · 판정 회의 참석자 |

## 템플릿 — 결과 보고

| 단계 | 동시 사용자 / 분당 요청 | p95 응답 | 에러율 | 병목 | 판정 |
|---|---|---|---|---|---|
| 평소 | | | | | |
| 지난 시즌 최고 | | | | | |
| 최고 × 1.5 | | | | | |
| 한계 탐색 | | | | 어디서 먼저 무너지나(DB·외부 API·앱 서버) | |

결론은 "통과 / 조건부 통과(증설·캐시 필요) / 실패" 셋 중 하나와, 그 근거 수치 한 줄.

## 채운 예시 — 시즌 오픈 대비 (2025.03, 수치는 비율로 일반화)

| 항목 | 내용 |
|---|---|
| 목적 | 시즌 오픈 직후 몰리는 요청(**5분 약 18만 요청**)을 흡수하는 서버 구성 찾기 |
| 방법 | 동시 접속 200 고정, 5분 증가 + 5분 유지, 작업 수를 단계별로 올리며 프론트·백엔드 대수와 사양을 바꿔 가며 반복 |
| 결과 | 목표의 **약 2.6배**(5분 약 48만 요청)까지 페이지 지연 없음 → 그 위 단계에서 지연 시작 |
| 알게 된 경계 | 프론트 서버 CPU가 **75%를 넘으면** 페이지 지연이 시작되고, 90~100%면 접속 자체가 밀린다 |
| 병목 순서 | 백엔드는 낮은 사양에서도 버텼고, **DB CPU가 먼저** 한계에 가까워졌다 |
| 증설 결정 | 프론트 인스턴스 1대가 버티는 요청량으로 최대 트래픽을 나눠 대수 산정. 한 달 뒤 재측정에서 대당 처리량이 **약 20% 줄어든 것**(화면 렌더링 방식 변경 영향 추정)을 찾아 대수를 다시 계산 |
| 실패 기록 | 일부 단계에서 API 서버 timeout으로 테스트가 끊겨 재시작 — 실패 회차도 결과표에 그대로 남김 |

판정: **조건부 통과** — 지연 경계(프론트 CPU 75%)를 넘지 않도록 대수를 맞추는 조건. 팀 공동 수행, 결과 보고서는 직접 작성.

## 체크리스트
- [ ] 성공 기준을 테스트 **전에** 숫자로 정했다
- [ ] 경로별 요청 비율을 운영 로그에서 가져왔다(한 API만 두드리지 않았다)
- [ ] 외부 결제·발송을 실제로 호출하지 않았다 — 모의로 대체했으면 결과에 명시
- [ ] 공유 환경이면 다른 팀에 시간·영향을 미리 알렸다
- [ ] 병목 위치와 조치(증설·캐시·쿼리)를 수치와 함께 남겼다
- [ ] 같은 조건으로 주기적으로 다시 쟀다 — 코드가 바뀌면 대당 처리량도 바뀐다

## 쓰지 않을 때
- 운영 지표에서 이미 원인이 보이는 성능 문제(느린 쿼리 하나)는 부하 테스트보다 쿼리 분석이 빠르다.
- 운영과 사양·데이터가 크게 다른 환경에서 낸 절대 수치는 판정에 쓰지 않는다. 변경 전후 **상대 비교**에만 쓴다.
