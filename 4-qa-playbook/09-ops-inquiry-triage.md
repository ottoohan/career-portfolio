# 09. 운영 문의 판정

> 운영 부서의 문의는 "결함인가, 운영자의 실수·오해인가, 정책을 묻는 것인가"부터 가른다. **판정에 따라 닫는 방법이 다르다.** 결함이어도 운영자가 오늘 할 수 있는 우회를 먼저 주고, 근본 수정은 티켓으로 넘긴다.

## 판정 순서

| 순서 | 묻는 것 | 확인하는 곳 |
|---|---|---|
| 1 | 실제로 무엇이 보이나 | 문의 화면 캡처, 해당 상품·회원 데이터 |
| 2 | 원인은 어디인가 | 데이터 → 코드 → 배포·설정 → 정책 순으로 내려간다([04. 원인 분석](04-root-cause-analysis.md)) |
| 3 | 누가 고칠 수 있나 | 운영자가 화면에서 / 데이터 보정이 필요 / 코드 수정이 필요 |
| 4 | 다시 생기지 않게 하려면 | 안내로 충분한가, 가드(저장 전 차단·경고)가 필요한가 |

## 판정 기준

| 판정 | 기준 | 예 |
|---|---|---|
| 시스템 결함 | 정해진 대로 썼는데 시스템이 틀리게 동작 | 잔액이 0원인데 탈퇴가 막힘 |
| 운영 실수 · 동작 오해 | 운영자의 설정·조작 실수, 또는 동작을 잘못 이해. 가드가 없어 실수가 그대로 통과한 경우도 여기에 넣는다 | 수량을 늘렸는데 품절 표시가 남음(품절 시 "마감" 표시가 따로 저장되는 걸 모름) |
| 정책 문의 | 동작은 맞고, 규칙을 묻는 것 | 결제 기한 안에는 품절 옵션도 결제되는 이유 |
| 원인 미확인 | 재현이 안 되거나 정보가 부족 | 요청자 PC에서만 생기는 현상 |

운영 실수·동작 오해로 판정한 건은 한 달 단위로 모아 비율을 낸다. 같은 유형이 반복되면 안내를 바꾸고, 안내로도 반복되면 가드로 바꾼다.

## 템플릿 — 문의 스레드 답글

```markdown
[판정] 시스템 결함 / 운영 실수·동작 오해 / 정책 문의 / 원인 미확인
[원인] <확인한 것 한두 줄. 데이터·코드·설정 중 어디서 확인했는지>
[오늘 할 수 있는 조치] <화면 경로까지: 메뉴 > 화면 > 버튼, 입력값>
[근본 수정] 필요 없음 / 티켓 <번호> (문제·기대 결과 형식)
[재발 방지] 안내 공유 / 가드 제안 / 해당 없음
```

## 채운 예시

```markdown
[판정] 시스템 결함 (같은 원인 재발)
[원인] 상품권을 사면 유효기간 1년짜리 수강으로 등록되는데, 탈퇴 검사가 잔액이 아니라
       수강 기간만 본다. 잔액이 0원이어도 수강 기간이 남아 있으면 탈퇴가 막힌다.
[오늘 할 수 있는 조치] 어드민 학습관리 > 수강생 관리 > 해당 상품권의 수강 종료일을 어제로 변경.
       처리 뒤 고객에게 탈퇴를 다시 시도하도록 안내.
[근본 수정] 티켓 등록 — 탈퇴 검사가 잔액을 보도록
[재발 방지] 같은 문의가 오면 위 조치로 바로 처리하도록 운영 채널에 공유
```

## 쓰지 않을 때

- 여러 고객에게 동시에 영향이 있는 장애는 이 양식이 아니라 장애 대응 절차로 간다.
- 개인정보 노출이 의심되면 판정보다 보안 담당 보고가 먼저다.
- 편의·표기 수준의 요청(정렬 순서, 문구)은 판정 없이 개선 백로그로 넘긴다.

## 체크리스트

- [ ] 판정 한 단어가 첫 줄에 있다
- [ ] 우회 조치가 화면 경로까지 적혀 있어 운영자가 혼자 따라 할 수 있다
- [ ] 결함이면 티켓 번호를 스레드에 남겼다
- [ ] 운영 실수·오해로 판정했다면 월 집계에 넣었다
- [ ] 같은 유형이 세 번째라면 안내 또는 가드를 제안했다
